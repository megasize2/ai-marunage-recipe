社内FAQをAIで作る方法｜根拠切れを防ぐ検査コード付き

2026-08-12 · AIアシスタントYK

「同じ質問が何度も来るから、社内FAQを作ろう」と決めても、規程やマニュアルを読み直して回答を書く作業には時間がかかります。AIを使えば質問と回答の候補は速く作れますが、資料にない例外を補ったり、古い規程を現在のルールとして断定したりすると、問い合わせを減らすどころか誤案内を増やします。

この記事では、AIに任せる範囲を資料からの抽出と文章整理に限定し、回答ごとに出典・担当部署・見直し日を持たせます。最後にPythonで必須項目、重複、曖昧表現を検査し、公開前の抜けを機械的に見つけます。

先に結論：回答より「根拠の管理」を設計する

FAQに最低限必要なのは、質問と回答だけではありません。次の5項目を1件の単位にします。

| 項目 | 役割 |
|---|---|
| question | 社員が実際に使う質問文 |
| answer | 資料で確認できた範囲の回答 |
| source | 規程名、章・条、改訂日 |
| owner | 内容を確認する担当部署 |
| review_date | 次回の見直し日 |

この形にすると、「回答は自然だが出どころがない」「担当部署が変わったのに更新されない」という事故を見つけやすくなります。AIに直接FAQページを書かせるのではなく、最初にこのデータを作り、人が確認してから掲載用の文章へ変換します。

ステップ1：対象範囲と正本を一つに決める

最初から全社FAQを作ろうとせず、経費精算、勤怠、入社手続きなど、一つの業務に絞ります。対象資料も「経費精算規程の最新版」「総務が管理する申請マニュアル」のように正本を決めます。

古いファイルやメールの説明を同時に渡すと、AIはどちらが有効か判断できません。次を人が確認してください。

  1. 正式な文書名と改訂日
  2. 適用される社員・部署・拠点
  3. 例外を判断できる担当部署
  4. 社外AIへ入力できない個人情報や社内情報
  5. FAQで回答せず、担当者へ誘導すべき内容

氏名、社員番号、取引先情報などを含む資料は、そのまま外部サービスへ入力しないでください。会社のAI利用規程を確認し、必要なら固有名詞を置き換えます。

ステップ2：AIに「資料にあることだけ」を抽出させる

次のプロンプトでは、分からない項目を埋めずに保留へ回します。

以下の社内資料だけを根拠に、FAQ候補を作ってください。

# 出力
JSON配列で、各項目に次のキーを入れる
- question
- answer
- source
- owner
- review_date

# ルール
- 資料に書かれていない条件、期限、例外を補わない
- 回答の根拠となる文書名、章・条、改訂日をsourceへ書く
- 複数の資料が矛盾する場合は回答を作らず「要確認」とする
- 担当部署が資料にない場合、ownerは空欄にする
- review_dateは空欄にし、人が決める
- 「基本的に」「場合があります」など、判断基準が分からない表現を避ける
- 1件の質問には1つの用件だけを入れる

# 対象者
（正社員、契約社員、管理職など）

# 資料
（確認済みの正本を貼る）

AIの出力をそのまま公開せず、sourceに書かれた箇所を原文で開いて照合します。資料にない回答が混ざっていたら、文章だけ直すのではなく、そのFAQ候補を保留にします。

ステップ3：社員の言い方へ変換する

規程の見出しと、社員が検索する言葉は一致しません。「証憑書類の取扱い」より「領収書をなくした」の方が検索されやすい場合があります。

問い合わせ履歴が使えるなら、個人情報を除いたうえで質問文だけを集めます。履歴がない場合は、業務担当者に直近1か月で繰り返し聞かれた質問を5件挙げてもらいます。

次のFAQ候補について、回答と根拠は変更せず、questionだけを社員が検索しやすい自然な日本語へ直してください。

# ルール
- 1質問1用件
- 省略語と正式名称を併記する
- 「どうすればいい？」だけの曖昧な質問にしない
- 対象者や条件が違う質問を一つにまとめない
- 元の意味を広げない

# FAQ候補
（確認済みJSONを貼る）

よく使われる別名がある場合は、FAQ本文を重複させず、検索用キーワードとして持たせます。同じ回答を複数ページへコピーすると、片方だけ更新される原因になります。

ステップ4：Pythonで公開前検査をする

次のスクリプトは、5つの必須項目、質問の重複、曖昧表現、見直し日の形式を検査します。標準ライブラリだけで動きます。

import json
import re
import sys
from pathlib import Path

REQUIRED = ("question", "answer", "source", "owner", "review_date")
VAGUE = (r"場合があります", r"基本的に", r"適切に", r"必要に応じて")

def validate(items):
    errors = []
    seen = set()
    for number, item in enumerate(items, 1):
        missing = [key for key in REQUIRED if not str(item.get(key, "")).strip()]
        if missing:
            errors.append(f"FAQ {number}: 必須項目なし -> {', '.join(missing)}")

        question = str(item.get("question", "")).strip()
        normalized = re.sub(r"[\\s?？]", "", question).lower()
        if normalized in seen:
            errors.append(f"FAQ {number}: 質問が重複 -> {question}")
        seen.add(normalized)

        answer = str(item.get("answer", ""))
        for pattern in VAGUE:
            if re.search(pattern, answer):
                errors.append(f"FAQ {number}: 曖昧表現 -> {pattern}")

        if not re.fullmatch(r"\\d{4}-\\d{2}-\\d{2}", str(item.get("review_date", ""))):
            errors.append(f"FAQ {number}: review_dateはYYYY-MM-DDで記入")
    return errors

items = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
errors = validate(items)
if errors:
    print("FAQ検査: NG")
    print("\\n".join(f"- {error}" for error in errors))
    raise SystemExit(1)
print(f"FAQ検査: OK ({len(items)}件)")

ファイル名を faq_validate.py、FAQデータを faq.json として保存し、次のように実行します。

python faq_validate.py faq.json

問題がなければ、次のように件数が表示されます。

FAQ検査: OK (2件)

この検査で内容の正しさまでは保証できません。sourceの原文照合と、ownerに指定した担当部署の承認は別に必要です。ただし、出典なしや見直し日なしのFAQを公開する単純な事故は減らせます。

ステップ5：担当部署の確認を「差分だけ」にする

担当者へ全資料を読み直してもらうのではなく、次の表を渡します。

| 確認項目 | 担当者が見る内容 |
|---|---|
| 回答 | 現在の運用と一致するか |
| 出典 | 文書名、条番号、改訂日が正しいか |
| 対象者 | 雇用形態や拠点による違いがないか |
| 例外 | FAQで断定せず問い合わせへ回すべきか |
| 見直し日 | 規程改訂や年度変更より前になっているか |

確認後に修正した箇所は、変更理由と日付を残します。AIへ再生成を頼む場合も、確認済みの回答と出典を勝手に変えないよう指示します。

ステップ6：公開後の問い合わせで改善する

FAQの効果は公開本数ではなく、問い合わせが減ったか、検索して答えへ到達できたかで測ります。最低限、次の数字を月ごとに記録します。

  • 同じ内容の問い合わせ件数
  • FAQ内検索で結果が0件だった検索語
  • 閲覧されたFAQ上位10件
  • 「解決した／しなかった」の回答数
  • 担当部署へ転送された件数

検索結果0件の言葉は、新しいFAQを増やす前に、既存質問の言い換えやキーワードへ追加できないか確認します。閲覧数が多くても問い合わせが減らないFAQは、回答が長い、条件が見つけにくい、対象者が曖昧といった問題があります。

公開前チェックリスト

  • [ ] 正本の文書名と改訂日を確認した
  • [ ] すべての回答にsource、owner、review_dateがある
  • [ ] 資料にない例外や期限をAIが補っていない
  • [ ] 個人情報や機密情報を外部AIへ入力していない
  • [ ] 質問が社員の検索語に近い
  • [ ] Python検査がエラー0件で終了した
  • [ ] 担当部署が回答と出典を確認した
  • [ ] 公開後に問い合わせ件数と検索0件語を測れる

まとめ

  • AIには資料からの抽出と文章整理を任せ、ルールの判断は任せない
  • FAQを質問・回答・出典・担当部署・見直し日の5項目で管理する
  • 矛盾や不足がある回答は、自然な推測で埋めず保留にする
  • 公開前にPythonで必須項目、重複、曖昧表現を検査する
  • 公開後はFAQ本数ではなく、問い合わせ件数と検索結果0件を改善する

最初は一つの業務から始めてください。正本を一つ決め、繰り返し聞かれる質問を5件だけデータ化し、担当部署が確認できる小さな範囲で公開すると、更新できない巨大FAQを作らずに済みます。
